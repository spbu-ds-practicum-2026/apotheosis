# Стенд на двух ноутбуках

| | Ноутбук 1 (`pc1.yml`) | Ноутбук 2 (`pc2.yml`) |
|---|---|---|
| etcd | etcd1, etcd2 | etcd3 |
| Feed DB (Patroni) | n1a, n2b, n3a (+ n4b) | n1b, n2a, n3b (+ n4a) |
| Сервисы | Feed, API Gateway, Recommender + его БД, Redis, хранилище | Feed, API Gateway |

Каждый узел кольца N1–N3 — кластер Patroni из двух участников на разных ноутбуках: мастер
и синхронная реплика. Кто мастер, решает Patroni.

## Запуск

1. На обоих ноутбуках: репозиторий на ветке, в `cluster.env` IP обоих ноутбуков (`hostname -I`).
2. Порты (если включён ufw):
   - ноутбук 1: `sudo ufw allow 2379,2380,2381,2382,5441:5444,8041:8044,8000,8001,8002,9000,6379/tcp`
   - ноутбук 2: `sudo ufw allow 2379,2380,5441:5444,8041:8044,8000,8001/tcp`
3. Запуск (в любом порядке, etcd и Patroni дождутся друг друга):
   ```bash
   cd services/deploy/cluster
   docker compose -f pc2.yml --env-file cluster.env up -d --build   # ноутбук 2
   docker compose -f pc1.yml --env-file cluster.env up -d --build   # ноутбук 1
   ```
4. Проверка:
   ```bash
   DC="docker compose -f pc1.yml --env-file cluster.env"   # на ноутбуке 2 — pc2.yml
   $DC exec n1a patronictl -c /etc/patroni.yml list        # кластер feed-n1: Leader и Sync Standby
   curl -s http://localhost:8001/health | python3 -m json.tool   # topology: кольцо и мастера
   $DC logs feed | grep "демо-данные"
   ```
5. Клиент на каждом ноутбуке — к своему Gateway: `API_URL=http://<IP этого ноутбука>:8000 python services/desktop/app.py`.

Первый запуск собирает образ Patroni (PostgreSQL 16 + Patroni), это несколько минут.

## Шпаргалка для защиты

Для каждой концепции: проблема → решение → гарантия → показ → ограничения. Подробные шаги — `docs/testplan.md`.

**1. Ненадёжная доставка (at-least-once).** Recommender или брокер могут быть недоступны, событие лайка нельзя терять.
Событие пишется в outbox одной транзакцией с лайком; фоновый отправитель досылает его в Redis Stream до успеха;
Recommender подтверждает (XACK) только после коммита, неподтверждённое забирается заново.
*Гарантия:* каждое событие доставляется хотя бы раз. *Показ:* T9, T14. *Ограничение:* возможны дубли — их снимает п. 2.

**2. Повторная обработка (идемпотентность, дедупликация).** Клиент повторяет запрос, брокер доставляет дважды.
`event_id` — первичный ключ лайка/просмотра в Feed, `pin_requests` для создания пина, `processed_events` в Recommender
(в одной транзакции с обновлением весов). *Гарантия:* эффект ровно один раз. *Показ:* T7, T8, T9.
*Ограничение:* клиент обязан сохранять event_id при повторе.

**3. Частичные отказы: обнаружение и реакция.** Recommender может зависнуть или упасть.
Таймаут 500 мс и circuit breaker; запасной путь — популярное из кэша. *Гарантия:* лента не пустеет.
*Показ:* T10. *Ограничение:* на время отказа лента не персональная.

**4. Single-master репликация с failover.** Узел БД может упасть.
Patroni: мастер + синхронная реплика на другом ноутбуке, лидерская аренда в etcd (ttl 15 с);
Feed читает мастера из etcd и повторяет запись с backoff до 30 с. *Гарантия:* подтверждённый лайк не теряется,
двух мастеров нет (leader lock + fencing). *Показ:* T11, T12. *Ограничение:* запись в узел недоступна ~15–20 с;
при отказе ноутбука 1 нет кворума etcd.

**5. Consistent hashing с переносом данных.** Нужно добавить узел, не перемешав все данные.
Кольцо с 256 токенами на узел, ключ — логин автора; `server.migrate add N4` копирует, переключает кольцо в etcd,
догоняет и удаляет. *Гарантия:* переезжает ~1/N ключей, только на новый узел; лайки идут во время переноса.
*Показ:* T13. *Ограничение:* «горячий» автор нагружает один узел.

**6. Eventual consistency.** Recommender хранит свою копию лайков и весов.
*Гарантия:* после прекращения операций копии сходятся (outbox + at-least-once + дедупликация).
*Показ:* T14 (`demo_tools consistency`). *Ограничение:* лайк влияет на ленту с задержкой до секунды.
