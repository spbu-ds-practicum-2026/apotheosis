# Техническое решение проекта «Лента картинок»

## Введение
- **Цель проекта:**  
  «Лента картинок» - учебный проект, реализующий прототип распределенной платформы для просмотра картинок, которые предположительно интересны пользователю, в формате бесконечной ленты. Проект демонстрирует ключевые принципы построения отказоустойчивых и масштабируемых распределённых приложений.
- **Задачи:**  
  - Реализовать платформу для просмотра и обмена пинами, работающую на нескольких узлах приложения.
  - Обеспечить формирование персонализированной ленты с корректным порядком выдачи контента для каждого пользователя.
  - Реализовать реплицированное хранилище пинов и очередь задач, которые переживают отказ отдельных узлов.
  - Закрепить на практике решения проблем распределённых систем: ненадёжной доставки, частичных отказов, распределения данных, согласованности и порядка событий.
- **Основания для разработки:**  
  Учебный групповой проект по курсу: «Основы распределённых вычислений», СПбГУ, 2026 г.

## Глоссарий
| Термин        | Определение |
|---------------|-------------|
| **Пользователь** | Зарегистрированный клиент системы, имеющий профиль и историю действий. |
| **Пин** | Базовая единица контента: изображение, видео или ссылка с метаданными (название, описание, теги, автор). |
| **Доска** | Коллекция пинов, созданная пользователем для группировки по темам; может быть публичной или приватной. |
| **Лента** | Персонализированный бесконечно прокручиваемый список пинов, формируемый для пользователя. |
| **Лайк** | Явное положительное действие пользователя, сигнал рекомендательной системе о релевантности пина. |
| **Просмотр** | Факт показа пина пользователю в ленте (impression). |
| **Тег** | Ключевое слово, описывающее содержание пина; используется для поиска и контентной фильтрации. |
| **Рекомендательная система** | Комплекс алгоритмов, анализирующих поведение пользователей и контент для подбора релевантных пинов. |
| **Коллаборативная фильтрация** | Метод рекомендаций на основе схожести пользователей или пинов («тем, кто лайкал A, также нравится B»). |
| **Контентная фильтрация** | Метод рекомендаций на основе характеристик контента (теги, категории, эмбеддинги). |
| **Эмбеддинг** | Векторное представление пользователя или пина в многомерном пространстве; близкие векторы означают схожесть объектов. |
| **Ранжирование** | Сортировка отобранных пинов по вероятности взаимодействия пользователя с ними. |
| **Брокер сообщений** | Компонент для асинхронной передачи событий (лайки, просмотры) между сервисами. |
| **Очередь** | Буфер сообщений, позволяющий развязать отправителя и получателя. |
| **Шард** | Независимый сегмент данных, размещённый на отдельном узле или группе узлов. |
| **Хеш-кольцо** | Способ распределения ключей по узлам (consistent hashing): узлы и ключи отображаются на кольцо, ключ принадлежит ближайшему узлу по часовой стрелке. |
| **Виртуальный узел** | Дополнительная точка хеш-кольца, принадлежащая физическому узлу; повышает равномерность распределения ключей. |
| **Реплика** | Копия данных, поддерживаемая для отказоустойчивости и распределения чтения. |
| **Мастер** | Реплика, принимающая записи в пределах своего шарда. |
| **Консистентность** | Свойство, гарантирующее согласованность состояния данных между репликами. |
| **Eventual consistency** | Модель согласованности, при которой при отсутствии новых обновлений все копии данных со временем сходятся к одному состоянию. Подходит для ленты, где небольшая задержка допустима. |
| **Failover** | Автоматическое переключение на резервный узел при отказе основного. |
| **Fencing** | Изоляция отказавшего мастера, исключающая его дальнейшие записи (защита от split-brain). |

## Функциональные требования
Система должна предоставлять следующие функции:
1. Авторизация и аутентификация пользователя.
2. Генерация ленты.
3. Бесконечный скроллинг.
4. Взаимодействие с контентом - пользователь должен иметь возможность отмечать понравившиеся изображения (например, ставить «лайк»).
5. Система должна учитывать взаимодействия пользователя (просмотры, лайки) для корректировки выдачи последующих картинок.

---

## Нефункциональные требования
1. Отказоустойчивость - выход из строя одного или нескольких узлов (частичный отказ) не должен приводить к полной неработоспособности приложения. Пользователь должен продолжать получать картинки (возможно, с деградацией качества рекомендаций).
2. Доступность - система должна отдавать приоритет доступности над строгой консистентностью (задержка в отображении лайка предпочтительнее недоступности ленты).
3. Время ответа на запрос новой порции картинок не должно превышать приемлемых значений, чтобы обеспечить плавность бесконечной прокрутки.
4. Использование механизмов кэширования (горячих данных) для часто запрашиваемых картинок и распределенного хранения статики.
5. Серверная часть разрабатывается с применением очередей сообщений и распределенных БД.

## Пользовательские сценарии
### Сценарий: авторизация в системе

1. Пользователь открывает приложение и вводит свои учетные данные (или регистрирует новый аккаунт).
2. Система проверяет данные и создает персональную сессию пользователя для формирования индивидуальной истории взаимодействий.

### Сценарий: просмотр бесконечной ленты

1. Пользователь прокручивает ленту картинок в клиентском приложении.
2. При приближении к концу текущего списка приложение автоматически запрашивает у системы следующую порцию изображений.
3. Система возвращает новый пакет картинок, и пользователь продолжает просмотр без задержек.

### Сценарий: взаимодействие с контентом (лайк)

1. Пользователь нажимает кнопку «лайк» на понравившейся картинке в ленте.
2. Клиентское приложение отправляет отметку о лайке в систему.
3. Система фиксирует действие пользователя и передает его в механизм рекомендаций для учета интересов при дальнейшей выдаче контента.

### Сценарий: просмотр своего профиля

1. Пользователь переходит в раздел своего профиля через клиентское приложение.
2. Система запрашивает и отображает персональную информацию пользователя, статистику (количество загруженных картинок, лайков) и его личную коллекцию контента.

### Сценарий: просмотр чужого профиля

1. Пользователь выбирает профиль другого участника системы (например, кликнув по имени автора картинки).
2. Клиентское приложение отправляет запрос на получение данных указанного пользователя.
3. Система возвращает публичную информацию чужого профиля (аватар, имя, публичные загрузки и коллекции), которую пользователь видит на экране.
